\section*{Introduction}
\addcontentsline{toc}{section}{Introduction}

When discussing methods for connecting to a self-hosted server at home, for example on the
\href{https://www.reddit.com/r/selfhosted/}{r/selfhosted} subreddit, \href{https://tailscale.com/}{Tailscale} is frequently recommended.

This recommendation is understandable, because connecting to a private home server is generally more complex than connecting to a publicly accessible server.
In many home networks, devices are located behind NAT and assigned IPv4 addresses that may change periodically\footnote{This is partly due to IPv4 address exhaustion.},
while firewalls often block incoming connections from outside the local network.

In some cases, a public IPv4 address is not available at all, because an internet service provider may use
\href{https://en.wikipedia.org/wiki/Carrier-grade_NAT}{CGNAT}. Under such conditions, external access to the network may remain unavailable
even when \href{https://en.wikipedia.org/wiki/Dynamic_DNS}{Dynamic DNS} is used and the relevant ports are forwarded on the router.

Tailscale addresses many of these limitations. When the Tailscale client is started, it connects to a
\href{https://tailscale.com/docs/concepts/control-data-planes}{control plane} that manages the Tailscale network, known as a
\href{https://tailscale.com/docs/concepts/tailnet}{tailnet}. The control plane maintains information about the devices in the network,
including their internal addresses and public keys, manages access to each device, and assists with \href{https://tailscale.com/blog/how-nat-traversal-works}{NAT traversal},
which can enable direct connections to a server. Rather than using the traditional VPN model,
in which traffic passes through a relay server to reach an internal subnet, Tailscale connects devices directly.
This reduces the number of intermediaries and may lower latency and decrease dependence on a single relay point
\footnote{A single point of failure still exists, since the tailnet is managed by the control plane rather than by a relay server.}.
Because all clients in the network communicate directly with one another, this architecture is commonly described as a \href{https://en.wikipedia.org/wiki/Mesh_networking}{mesh VPN}.

In practice, Tailscale allows a device to join a tailnet and then access other devices through their assigned addresses.
This reduces the need to configure peers on each device, open ports, or manually manage routing.

The same approach can also be useful for multiplayer gaming with friends.
However, a simpler alternative in this context is \href{https://www.radmin-vpn.com/}{Radmin VPN}, which provides similar functionality.
Since it is proprietary software, users cannot independently verify how it operates or determine whether it contains malicious code.

Motivated by an interest in the internal design of Tailscale, this project aims to develop a VPN solution, identify implementation issues through practical experience,
and potentially create a tool for gamers to use for online play. Even if the project does not reach full completion, it is expected to provide substantial practical learning value.

\section{Researching existing solutions} \label{existingsolutions}

An interest in \href{https://en.wikipedia.org/wiki/Self-hosting_(network)}{self-hosting}
various services on personal servers motivated an emphasis on maintaining control over personal data
and reducing reliance on third-party infrastructure.
For this reason, solutions such as Tailscale and Radmin VPN were considered unsuitable in certain aspects:
\begin{itemize}
  \item Radmin VPN is fully proprietary, meaning that both the server-side and client-side components
        are controlled by the vendor. As a result, users have limited ability to verify the behavior
        of the software or audit its security guarantees.
  \item Tailscale provides an open-source client implementation; however, its control plane remains proprietary
        and governs client coordination and network management. Consequently, compromise of the control infrastructure
        could potentially expose connected devices unless additional security measures, such as firewall configuration,
        are applied. Nevertheless, Tailscale represents a practical balance between usability and security.
\end{itemize}

Projects such as \href{https://syncthing.net/}{Syncthing} and \href{https://yggdrasil-network.github.io/}{Yggdrasil}
demonstrate alternative decentralized approaches in which each device independently determines trust relationships
without relying on a centralized authority responsible for connection management.

In particular, the networking model used by Yggdrasil was of significant interest.
Within this architecture, each client simultaneously functions as a server, while an IPv6 address also represents
the node's public key.
This design enables packets to be encrypted directly using the destination address, ensuring that only the node
possessing the corresponding private key can decrypt the transmitted data.
As a result, communication confidentiality can be maintained without dependence on a centralized authority,
while intermediate peers merely relay encrypted traffic toward the intended recipient.

However, fully decentralized systems introduce the challenge of peer discovery.
Without a central coordination server, nodes require alternative methods for locating peers on the Internet.
Historically, \href{https://en.wikipedia.org/wiki/BitTorrent}{BitTorrent}
relied on \href{https://en.wikipedia.org/wiki/BitTorrent_tracker}{trackers}
to identify peers participating in a particular file-sharing session.
This approach created a dependency on centralized infrastructure despite the distributed nature of the protocol itself.
\footnote{The use of multiple trackers can improve resilience, although the architecture still retains partially centralized characteristics.}

To address this limitation, modern
\href{https://en.wikipedia.org/wiki/Comparison_of_BitTorrent_clients}{BitTorrent clients}
commonly employ a \href{https://en.wikipedia.org/wiki/Kademlia}{Kademlia}-based
\href{https://en.wikipedia.org/wiki/Distributed_hash_table}{distributed hash table},
referred to as \href{https://en.wikipedia.org/wiki/Mainline_DHT}{Mainline DHT}.
In this model, each peer participates in a distributed tracking infrastructure,
eliminating dependence on a single centralized server for peer discovery.
Consequently, peer discovery remains functional even if all dedicated trackers become unavailable.
A detailed explanation of this mechanism is provided in the video
\href{https://www.youtube.com/watch?v=1QdKhNpsj8M}{Kademlia, Explained}.

Another relevant project is \href{https://radicle.xyz/}{Radicle},
which applies peer-to-peer networking principles to
\href{https://en.wikipedia.org/wiki/Git}{Git version control}.
Although Git itself is inherently distributed, collaboration is frequently facilitated through centralized
\href{https://en.wikipedia.org/wiki/Forge_(software)}{forge platforms}
such as \href{https://github.com/}{GitHub} and \href{https://about.gitlab.com/}{GitLab}.
Radicle introduces its own protocol, named
\href{https://app.radicle.xyz/nodes/iris.radicle.xyz/rad%3Az3gqcJUoA1n9HaHKufZs5FCSGazv5}{Heartwood},
which utilizes a \href{https://radicle.xyz/guides/protocol}{gossip protocol}
for peer and repository discovery.

\newpage

For example, consider the following peer topology:

\begin{figure}[H]
  $$ A \leftrightarrow B \leftrightarrow C \leftrightarrow D $$
  \caption{A diagram illustrating connections between peers}
\end{figure}

Suppose peer A intends to communicate with peer D but does not possess its network address.
Peer A propagates a gossip request to peer B, which forwards the request to peer C, and eventually to peer D.
Responses are then routed back through the network.
While this example demonstrates linear propagation, practical implementations distribute requests simultaneously
through multiple peers across the network.
To prevent excessive propagation and denial-of-service amplification, each peer stores identifiers of previously processed requests
and ignores duplicates.
This mechanism enables communication and information exchange even in the absence of direct connectivity between peers.

Additional investigation into peer-to-peer networking technologies led to the discovery of
\href{https://www.youtube.com/watch?v=RwAt36Xe3UI}{iroh},
a networking library implemented in \href{https://rust-lang.org/}{Rust}.
The library provides abstractions for establishing peer-to-peer communication with minimal configuration complexity.
Preliminary evaluation indicated that the library satisfies many of the requirements identified for decentralized networking systems
and may therefore be suitable for future projects involving peer-to-peer communication.

\section{Planning} \label{planning}

At the current stage of the project, the development of a fully original protocol is not considered feasible due to the significant amount of research and implementation effort required.
Instead, the implementation will be based on existing transport protocols and networking techniques.

UDP is considered as the primary transport protocol because it simplifies the implementation of
\href{https://en.wikipedia.org/wiki/UDP_hole_punching}{NAT hole punching}.
However, the use of UDP also requires additional mechanisms for
\href{https://www.reddit.com/r/networking/comments/a8c42z/}{reliable delivery}
and
\href{https://en.wikipedia.org/wiki/Network_congestion#Congestion_control}{congestion and rate control}.
Implementing these mechanisms from scratch is outside the scope of the available development time for the diploma project.

\subsection{Core functionality} \label{corefunctionality}

During the initial launch of the application, a cryptographic key pair is generated.
The public key serves as the identifier of a peer.
To establish a connection, each peer provides the identifier of the other peer, after which peer discovery and connection establishment are performed automatically.
Manual specification of network endpoints is therefore unnecessary, similarly to the approach used in iroh.

IP addresses are derived cryptographically from the peer identity unless explicitly specified in the configuration.

Connection failures are handled automatically in the background.
If a connection attempt fails, repeated reconnection attempts are performed until connectivity is restored.
The implementation is also intended to support network changes.
For example, if the IP address of a peer changes, packets should subsequently be transmitted to the updated destination address, similarly to the behavior of WireGuard.

\subsection{Core choices}

Rust was selected as the implementation language because it is also used by iroh, which is planned to be integrated into the final application.

The networking stack is planned to initially use UDP, followed by QUIC.
Starting with UDP provides a lower-level foundation for understanding and implementing the required networking functionality.
Additionally, TCP-based NAT hole punching will be investigated to evaluate its feasibility within the project context.

For asymmetric cryptography,
\href{https://en.wikipedia.org/wiki/EdDSA#Ed25519}{Ed25519}
was selected due to its widespread adoption in systems such as SSH, WireGuard, and iroh.
For symmetric encryption,
\href{https://en.wikipedia.org/wiki/ChaCha20-Poly1305}{ChaCha20}
was selected based on its performance characteristics and broad practical adoption.
For hashing functions,
\href{https://en.wikipedia.org/wiki/BLAKE_(hash_function)}{BLAKE3}
and
\href{https://en.wikipedia.org/wiki/SHA-2}{SHA-2}
are considered suitable choices for the implementation.

\section{Peer discovery}

After establishing UDP-based communication, it becomes necessary to replace direct IP addressing with node identifiers.
To achieve this, a discovery server is required to associate node identifiers with their corresponding IP addresses.

\subsection{Discovery server}

The implemented discovery server uses the same UDP-based protocol,
where messages are represented as plain text strings in the following format:
\texttt{command|arguments}.

When the discovery server receives a command, it also obtains the source address of the sender.
Consequently, after receiving the command \texttt{register|node id}, the server can associate the node identifier with the sender's address, for example:
\mintinline{js}|nodes["node id"] = "source address"|
using a \href{https://en.wikipedia.org/wiki/Hash_table}{hash map}.

\subsection{A node/peer}

Each node registers itself with the discovery server and subsequently requests
the address associated with the target node identifier.
This process is executed continuously in a loop, allowing the node to repeatedly
register itself, retrieve the target address, and transmit messages to the target node.

\subsection{Observed limitations}

Initial experiments were conducted with both nodes connected to the same residential Wi-Fi network.
Under these conditions, incoming packets were not successfully delivered between the nodes.
This behavior is likely related to router-specific NAT handling or limitations in local packet forwarding mechanisms.
Consequently, alternative peer discovery and communication mechanisms are required for nodes operating within the same local network.

One possible solution is the use of \href{https://en.wikipedia.org/wiki/Zero-configuration_networking}{Zeroconf} technologies,
which enable automatic service advertisement and discovery within local networks.
Such mechanisms allow nodes located in the same network to establish communication without relying on an external discovery server.

The \href{https://docs.iroh.computer/connecting/local-discovery}{Iroh} framework, for example, implements an mDNS-like local discovery mechanism that can be enabled when required.

Another potential limitation arises when both nodes are located in different networks but operate behind the same CGNAT infrastructure
\footnote{Devices share the same public IPv4 address while maintaining different internal private addresses}.
In this scenario, the discovery server cannot determine the internal addresses assigned within the CGNAT environment, which may prevent successful peer-to-peer connectivity.

\section{TCP hole punching}

\href{https://en.wikipedia.org/wiki/TCP_hole_punching}{TCP hole punching} operates similarly to UDP hole punching.
In principle, it is sufficient for both peers to send a \texttt{SYN} packet to each other's network addresses,
after which subsequent packets may traverse the NAT device successfully.

The primary challenge lies in implementing this behavior programmatically.
Most standard networking libraries support TCP sockets operating either in \emph{connect} mode or \emph{listen} mode,
while the \emph{connect} mode typically permits communication with only a single remote endpoint.

The \href{https://crates.io/crates/socket2}{socket2} Rust library provides access to operating system specific APIs
that allow TCP sockets to be reused across multiple destination addresses while preserving the same local port configuration.
This functionality can be employed to experimentally evaluate TCP hole punching behavior.

\subsection{Reusing the same socket}

Attempting to create multiple \href{https://en.wikipedia.org/wiki/Network_socket}{sockets} bound to the same local address
normally results in an ``Address already in use'' error. Modern operating systems commonly provide the \texttt{SO\_REUSEPORT} socket option,
which allows multiple sockets to share the same local address and port combination.

Using this mechanism, a node may first establish a connection to a discovery server in order to obtain a local address assignment.
Subsequently, additional sockets may reuse the same local address and port when attempting peer-to-peer communication.

An example implementation using the \href{https://crates.io/crates/socket2}{socket2} library is shown below:

\begin{figure}[H]
  \begin{minted}{rust}
use std::io;
use socket2::{Domain, Protocol, Socket, Type};

// Creates a TCP socket with SO_REUSEPORT
fn create_socket() -> io::Result<Socket> {
    let socket = Socket::new(Domain::IPV4, Type::STREAM, Protocol::TCP.into())?;
    socket.set_reuse_port(true)?; // sets SO_REUSEPORT for the socket
    Ok(socket)
}

fn main() {
    // First connect to a discovery server, so OS will give us a local addr
    let first_socket = create_socket().unwrap();
    let addr = "127.0.0.1:4444".parse().into(); // <-- discovery server
    first_socket.connect(&addr.into()).unwrap(); // establish a connection with discovery server

    let local_addr = first_socket.local_addr().unwrap()
    println!("local addr: {}", local_addr); // will print out 127.0.0.1:<random port>

    let second_socket = create_socket().unwrap();
    second_socket.bind(local_addr).unwrap(); // reuse same ip:port as in first socket
    second_socket.listen(128).unwrap(); // run socket in listen mode
}
  \end{minted}
  \caption{Example usage of the \texttt{socket2} library for creating reusable sockets}
\end{figure}

Without the \mintinline{rust}|Socket::set_reuse_port(true)| call, the example fails with an ``Address already in use'' error.
This behavior can be reproduced by replacing \texttt{true} with \texttt{false}.

\subsection{First attempt}

Migrating the discovery server implementation from UDP to TCP required relatively minor modifications.
In particular, a dedicated thread was introduced for each incoming connection in order to prevent premature socket termination.

The peer node implementation introduced additional complexity.
Unlike UDP communication, TCP requires an established connection before data transmission can occur.
Consequently, a node must either initiate a connection attempt to another peer or transition into a \emph{listen} state while awaiting incoming connections.

The initial implementation, corresponding to commit \href{https://github.com/dankmolot/petope/tree/3e83b3}{3e83b3},
operated successfully in a localhost environment where both nodes communicated through the \href{https://en.wikipedia.org/wiki/Loopback}{loopback} interface.
However, experiments involving separate physical devices were unsuccessful.
This result suggested that connection establishment and listening operations would need to occur concurrently, which proved difficult to implement using synchronous Rust code.

To address this limitation, the \href{https://tokio.rs/}{Tokio} asynchronous runtime was introduced.
Tokio enables concurrent execution of connection attempts and listener tasks within the same application context.

\subsection{Second attempt}

The second implementation was developed following the \href{https://tokio.rs/tokio/tutorial}{Tokio tutorial},
which presents examples based on the \href{https://github.com/tokio-rs/mini-redis/}{mini-redis} project.
The tutorial provided a structured approach for implementing asynchronous communication and protocol handling.

A simple \href{https://en.wikipedia.org/wiki/Frame_(networking)}{framing} mechanism was implemented,
enabling the use of Rust enumerations for structured input and output message handling.

Both the discovery server and node implementations were rewritten to use asynchronous Tokio TCP sockets.
In the revised design, each node launches a TCP listener in the background during initialization, registers itself with the discovery server once,
and then repeatedly attempts to establish a connection with another node.

This implementation successfully established peer-to-peer TCP communication across different networks.
The experimental setup consisted of one node operating on a notebook connected to a residential Wi-Fi network and another node operating on a mobile device connected through a cellular network.

\subsection{Nodes behind the same NAT}

Nodes located behind the same NAT device were still unable to establish direct communication.
This behavior was expected because peers attempted to connect using their public IP addresses.
When packets addressed to the public IP re-enter the router from the internal network,
the router may be unable to determine the appropriate internal destination and therefore discard the packets.

\newpage

The \href{https://en.wikipedia.org/wiki/Network_address_translation#NAT_hairpinning}{NAT hairpinning} (or \emph{NAT loopback})
feature was designed to address this issue. The router used during experimentation is listed among devices supporting this functionality
according to the vendor documentation \href{https://www.asus.com/support/faq/1043024/}{provided by ASUS}. However, the observed behavior did not fully match the expected functionality.
In the \href{https://www.snbforums.com/threads/asus-ac86u-firmware-merlin-386-11-nat-loopback-not-working-please-help.85974/}{forum discussion},
the user \texttt{ColinTaylor} notes that NAT loopback support may depend on explicit port forwarding configuration, which this implementation intentionally avoids.

This limitation motivates the discussion presented in the following section.

\section{Multicast DNS}

In addition to discovering nodes over the Internet, peer discovery can also be performed using a form of
\href{https://en.wikipedia.org/wiki/Service_discovery}{service discovery}, specifically
\href{https://en.wikipedia.org/wiki/Multicast_DNS}{Multicast DNS (mDNS)}.
This approach enables a node to advertise its presence within a local network, allowing other nodes
to discover and connect to it. Consequently, nodes located on the same local network can establish
connections without requiring Internet connectivity.

\begin{tcolorbox}
  This approach does not enable communication between nodes located in different networks behind the same
  carrier-grade NAT (CGNAT), unless the Internet service provider supports NAT hairpinning.
  IPv6 connectivity mitigates this limitation.
\end{tcolorbox}

The \href{https://crates.io/crates/mdns-sd}{\texttt{mdns-sd}} Rust library was used to implement
service discovery functionality. The integration primarily required replacing the previously implemented
discovery server with mDNS-based discovery.

\subsection{Implementation}

The integration of mDNS functionality was relatively straightforward due to the simplicity of the library API,
which is conceptually similar to the previously implemented discovery client.
The following example demonstrates the creation and registration of a service
\footnote{A service record contains the service type, IP addresses, hostname, identifier, and optional properties.}:

\end{figure}

\newpage

Service discovery is implemented as follows:

\begin{figure}[H]
  \begin{minted}{rust}
// fullname consists in form of identification + service type
let node_fullname = format!("{}.{}", node_id, "_petope._tcp.local.");
let receiver = sd.browse("_petope._tcp.local.")?;

loop {
    // ServiceDaemon will automatically search and resolve services for us
    let event = receiver.recv_async().await?;
    match event {
        // we just need to listen for resolved events
        ServiceEvent::ServiceResolved(svc) => {
            // Make sure that service has right identification
            if svc.get_fullname() == node_fullname.as_str() {
                let addresses = svc.get_addresses_v4();
                println!("discovered {} with addresses {:?}", node_id, addresses);
                sd.stop_browse("_petope._tcp.local.")?;

                // create SocketAddr that consists from first ipv4 address + service port
                return Ok(SocketAddr::V4(SocketAddrV4::new(
                    addresses.iter().next().unwrap().to_owned(),
                    svc.get_port(),
                )));
            }
        }
        // ignore all other events
        _ => {}
    };
}
  \end{minted}
  \caption{Discovery of peer services and retrieval of peer IP addresses using \texttt{mdns-sd}}
\end{figure}

The function shown above blocks until the target node is discovered, after which it returns the corresponding
network address that is subsequently used to establish a connection. One important constraint is that the
service name component in the service type format
(\textbf{\_name}.\_protocol.domain) cannot exceed 15 characters.

Experimental evaluation demonstrated that node discovery occurs with low latency, typically within a fraction
of a second on a local network. The complete implementation is available in commit
\href{https://github.com/dankmolot/petope/tree/0915f06ad2b44db91ace9968bc6654252927c25b}{0915f0}.

\section{Developing the Final Application}

\subsection{Configuration} \label{sec:appconfig}

The
\href{https://en.wikipedia.org/wiki/Public-key_cryptography}{cryptographic key pair}
serves not only as a security mechanism but also as the identity of a peer.
The public key is used both for peer discovery and for establishing connections.
Consequently, the private key must be persisted so that the application maintains a stable identifier across executions and can reliably connect to previously known peers.

For simplicity, both the private key and peer identifiers are stored in a single configuration file.
\footnote{An alternative design could separate the private key into a dedicated file.}
If no private key is present in the configuration, the application automatically generates one and stores it in the configuration file.

Because the configuration must support both reading and modification while preserving existing comments and formatting, the
\href{https://toml.io/en/}{TOML}
format was selected together with the Rust library
\href{https://crates.io/crates/toml_edit}{\texttt{toml\_edit}},
which preserves the original document structure during modification.

To facilitate local testing, the application allows the configuration file path to be specified through
command-line arguments. This functionality is implemented using the \texttt{clap} library.

\begin{figure}[H]

The \texttt{clap} library additionally provides automatically generated help messages and error handling.

\newpage

The following function either parses a
\href{https://en.wikipedia.org/wiki/Base64}{Base64}-encoded private key
from the configuration file or generates a new key using
\href{https://docs.rs/iroh/latest/iroh/struct.SecretKey.html#method.generate}{\texttt{SecretKey::generate()}}.
If a new key is generated, the updated configuration is written back to disk.

\begin{figure}[H]
  \begin{minted}{rust}
fn get_or_generate_secret_key(path: &str, doc: &mut DocumentMut) -> Result<SecretKey> {
    // get a global "private_key" value from parsed file
    if let Some(encoded) = doc.get("private_key").and_then(|v| v.as_str()) {
        // try to parse string from base64 into bytes
        let decoded =
            utils::base64_decode(encoded).context("private key must be encoded in base64")?;

        // convert to &[u8] and use TryInto which is implemented in SecretKey
        decoded
            .as_slice()
            .try_into()
            .context("private key must be valid ed25519 key bytes encoded in base64")
    } else {
        // No value, no problem, just generate a new
        let key = SecretKey::generate();

        // insert base64 encoded bytes of private key into document
        doc.insert(
            "private_key",
            utils::base64_encode(&key.clone().to_bytes()).into(),
        );

        // and write back to the original file
        std::fs::write(path, doc.to_string())
            .with_context(|| format!("write {} with generated private key", path))?;

        Ok(key)
    }
}
  \end{minted}
  \caption{Function for parsing or generating a private key}
\end{figure}

Since the private key is only required during endpoint creation,
\footnote{The private key is used exclusively during endpoint initialization and does not need to be retained afterward.}
the remaining configuration data, such as peer definitions, is parsed independently.

\begin{figure}[H]
  \begin{minted}{rust}
use iroh::{EndpointId, SecretKey};
use toml_edit::{DocumentMut, Item, Table};

#[derive(Debug, Clone)]
pub struct Config {
    pub peers: Vec<Peer>,
}

#[derive(Debug, Clone)]
pub struct Peer {
    pub id: EndpointId,
}

impl Config {
    fn parse(doc: DocumentMut) -> Result<Self> {
        // iterate over array of tables which looks like this in toml
        // [[peer]]
        // ...
        //
        // [[peer]]
        // ...
        let mut peers = Vec::new();
        if let Some(arr) = doc.get("peer").and_then(Item::as_array_of_tables) {
            for (i, t) in arr.iter().enumerate() {
                peers.push(
                    // here is parsing of each individual peers happens
                    Peer::parse(t).with_context(|| format!("parse a [[peer]] at index {}", i))?,
                );
            }
        }

        Ok(Config { peers })
    }
}

impl Peer {
    fn parse(t: &Table) -> Result<Self> {
        // gets "id" key as a string
        let id = t
            .get("id")
            .and_then(Item::as_str)
            .ok_or_else(|| anyhow!("expected an `id` but got nothing"))?;

        // Use alias to PublicKey::from_z32 to parse z32 string to public key
        let id = EndpointId::from_z32(id).context("parse `id` as an EndpointId")?;

        Ok(Peer { id })
    }
}

\subsection{TUN device} \label{sec:apptun}
A \href{https://en.wikipedia.org/wiki/TUN/TAP}{TUN device} is a \href{https://en.wikipedia.org/wiki/Network_virtualization}{virtual network interface}
that enables software applications to transmit and receive \href{https://en.wikipedia.org/wiki/Internet_Protocol}{IP packets}. TUN devices are commonly used in VPN implementations
\footnote{Certain implementations use TAP devices instead, which operate at the MAC layer and provide access to Ethernet frames.},
and are suitable for this project because they allow IP addresses to be derived from peer endpoint identifiers, enabling communication through standard networking software.

The \href{https://crates.io/crates/tun-rs/}{\texttt{tun-rs}} library was selected because it provides support for all major desktop operating systems.

\newpage

To initialize a TUN device, \texttt{tun-rs} provides a concise configuration interface:
\begin{figure}[H]
  \begin{minted}{rust}

    DeviceBuilder::new()
        .name("petope0") // device name that is shown in ifconfig
        .mtu(65535) // MTU, usually 1500, minimum 1280 for ipv6 on Linux
        .ipv4("10.0.0.1", 32, None)
        .ipv6("fdaa::beaf", 128)
        .layer(tun_rs::Layer::L3) // specify L3 for TUN device, L2 for TAP
        .build_async()
}

  \label{code:create_tun}

To transmit and receive IP packets, the library provides a higher-level abstraction over
\href{https://docs.rs/tun-rs/2.8.3/tun_rs/struct.AsyncDevice.html}{AsyncDevice}
through the \href{https://docs.rs/tun-rs/2.8.3/tun_rs/async_framed/index.html}{async\_framed}
module. This abstraction exposes an asynchronous interface for packet processing, avoiding the need
for manual manipulation of raw byte streams.

\subsubsection{About huge MTU} \label{sec:hugemtu}
As shown in Listing~\ref{code:create_tun}, the TUN device is configured with an MTU value of 65535.

This configuration was motivated by the discussion presented in the
\href{https://yggdrasil-network.github.io/2018/07/13/about-mtu.html}{Yggdrasil blog post}
regarding large MTU values and \href{https://en.wikipedia.org/wiki/Path_MTU_Discovery}{Path MTU Discovery}.
Path MTU Discovery enables intermediate systems to notify endpoints when packets exceed the supported transmission size, allowing fragmentation to occur at an appropriate MTU.

A larger MTU may reduce fragmentation overhead in future iterations of the system, potentially decreasing both bandwidth overhead and CPU utilization associated with packet fragmentation.

\subsubsection{Adding more routes}
At this stage, the TUN device only contains locally assigned IP addresses. However, the operating system routing table must also contain routes for peer addresses
(see Section~\ref{sec:apppeers}) so that packets destined for peers are forwarded through the TUN interface.

To manage routing entries, the \href{https://crates.io/crates/net-route}{\texttt{net-route}} library was used because it provides cross-platform route manipulation support.
The following example demonstrates how to add an IPv4 route associated with the TUN device:

\subsection{Router} \label{sec:approuter}

The router component is responsible for transmitting and receiving IP packets.
Consequently, an efficient mechanism for transferring packet data between asynchronous tasks is required.

\href{https://en.wikipedia.org/wiki/Channel_(programming)}{Channels} are commonly used for communication between threads and asynchronous tasks.
Tokio provides the \href{https://docs.rs/tokio/latest/tokio/sync/mpsc/index.html}{\texttt{tokio::sync::mpsc}}
module for this purpose. However, standard queue-based channels preserve older messages until they are processed, thereby prioritizing earlier packets over more recent ones.
Such behavior may negatively affect latency-sensitive workloads, including
\href{https://en.wikipedia.org/wiki/Real-time_communication}{real-time communication} systems.

To address this limitation, the \href{https://github.com/brunocodutra/ring-channel}{\texttt{ring-channel}} library was selected.
This library implements a \href{https://en.wikipedia.org/wiki/Circular_buffer}{ring-buffer}-based channel
with \href{https://en.wikipedia.org/wiki/Non-blocking_algorithm}{lock-free} synchronization semantics.
When the buffer capacity is exceeded, older packets are overwritten by newer packets, enabling the system to discard stale data during periods of overload.

Since data received from the TUN device consists of raw byte sequences, the \href{https://crates.io/crates/etherparse}{\texttt{etherparse}}
library is used to parse IP packets. The following example illustrates its usage within the router implementation:
\begin{figure}[H]
  \begin{minted}{rust}
fn route(
    // bytes received from TUN device
    bytes: Bytes,
    // ring-channel buffer destined to TUN device
    to_network_tx: &RingSender<Bytes>
) -> Result<()> {
    // parse bytes into a IP packet from etherparse library
    let ip = IpSlice::from_slice(&bytes[..]).context("parse incoming ip packet")?;
    // IpAddr from where packet has come
    let src = ip.source_addr();
    // IpAddr where packet is destined
    let dst = ip.destination_addr();

    // this is local packet, just return it back to kernel
    if src == dst {
        let _ = to_network_tx.send(bytes);
        return Ok(());
    }

    // TODO: send packets to different peers based on IP address
    
    Ok(())
}
  \end{minted}
  \caption{Routing function that parses raw bytes into IP packets for address-based routing}
\end{figure}

This implementation already enables local packet processing through the TUN interface without requiring complex routing logic.
The existing Rust ecosystem significantly reduces implementation complexity by providing reusable abstractions for IP packet parsing and asynchronous networking operations.

\subsection{Peers} \label{sec:apppeers}

The peer component of the application is responsible for connection management and data transmission.
The router component forwards packets received from the TUN device to the corresponding peer based on the destination address.

\subsubsection{Converting peer identifiers to IP addresses}

The address assignment approach is inspired by the design of Yggdrasil, where IPv6 addresses are derived from node public keys.
A similar mechanism is implemented in this project.
\begin{figure}[H]
  \begin{minted}{rust}
// converts EndpointId into an ipv4 address in 10.0.0.0/8 subnet
fn ipv4_from_id(id: &EndpointId) -> Ipv4Addr {
    Ipv4Addr::new(10, id[0], id[1], id[2])
}

// joins two u8 integers into one u16 integer
fn u8_pair(a: u8, b: u8) -> u16 {
    ((a as u16) << 8) | b as u16
}

// converts EndpointId into an ipv6 address in fd22::/16 subnet
fn ipv6_from_id(id: &EndpointId) -> Ipv6Addr {
    Ipv6Addr::new(
        0xfd22,
        u8_pair(id[0], id[1]),
        u8_pair(id[2], id[3]),
        u8_pair(id[4], id[5]),
        u8_pair(id[6], id[7]),
        u8_pair(id[8], id[9]),
        u8_pair(id[10], id[11]),
        u8_pair(id[12], id[13]),
    )
}

\end{figure}

These functions allow the application to generate deterministic IP addresses for both the \emph{TUN interface} and connected \emph{peers}.
Since the addresses are derived directly from the public key, both communication endpoints independently obtain identical address assignments.

The previous examples omit the implementation of connection caching.
Since the application is asynchronous, cached connections may be accessed concurrently by multiple threads and may also be replaced during runtime.
One possible synchronization primitive is
\href{https://doc.rust-lang.org/std/sync/struct.Mutex.html}{\texttt{std::sync::Mutex}},
although connections are expected to be read significantly more frequently than modified.
A more suitable alternative is
\href{https://doc.rust-lang.org/std/sync/struct.RwLock.html}{\texttt{std::sync::RwLock}},
which supports concurrent read access.
In this implementation,
\href{https://docs.rs/arc-swap/latest/arc_swap/}{\texttt{arc\_swap}}
is used instead, as it provides efficient atomic replacement of shared values with minimal synchronization overhead.

        self.conn
            .load_full()
            // return a connection only if it wasn't closed
            .filter(|conn| conn.close_reason().is_none())
    }

    pub async fn get_connection(&self) -> Result<Arc<Connection>, ConnectError> {
        // try to get an existing connection
        if let Some(conn) = self.try_get_connection() {

\subsubsection{Requesting packet fragmentation}

The remaining functionality involves transmitting and receiving IP packets between peers.
As described in Section~\ref{sec:hugemtu}, the TUN device is configured with an MTU value of \emph{65535}, which exceeds the typical Ethernet MTU of approximately 1500 bytes.
Consequently, Path MTU Discovery is required to ensure that packets are fragmented appropriately.

The \texttt{iroh} connection interface provides the minimum supported MTU, which can be used to generate ICMP responses instructing the operating system to reduce packet size.
Although ICMP is commonly associated with utilities such as \texttt{ping}, it also plays an essential role in network error reporting and path MTU discovery.
Blocking all ICMP traffic may negatively affect network functionality and should generally be avoided.
Instead, filtering should be limited to specific message types when necessary.

According to
\href{https://datatracker.ietf.org/doc/html/rfc4443#section-3.2}{RFC 4443},
ICMPv6 defines the \emph{Packet Too Big} message (type 2, code 0), which informs the sender that the transmitted packet exceeds the supported MTU.
The response must also include a portion of the original IP packet.
\begin{figure}[H]
  \begin{minted}{rust}
// returns an icmp response that fragmentation is needed, payload must be the same as ip slice
pub fn fragmentation_needed_response(ip: &IpSlice, payload: &[u8], mtu: usize) -> BytesMut {
    match ip {
        IpSlice::Ipv4(v4) => {} // very similar to ipv6 version
        IpSlice::Ipv6(v6) => {
            let header = v6.header();
            // convert given mtu in u32, or use maximum u32 integer
            let mtu = mtu.try_into().unwrap_or(std::u32::MAX);
            // create a packet destined back to source with PacketTooBig message
            let builder = PacketBuilder::ipv6(header.destination(), header.source(), HOP_LIMIT)
                .icmpv6(Icmpv6Type::PacketTooBig { mtu });

            // cut original IP packet so it will fit into MTU
            let payload_len = payload.len().min(mtu as usize - header.slice().len());
            let payload = &payload[..payload_len];

            // write icmp packet into a buffer and return it
            let mut writer = BytesMut::with_capacity(builder.size(payload.len())).writer();
            builder.write(&mut writer, payload).unwrap();
            writer.into_inner()
        }
    }
}
  \end{minted}
  \caption{Function that creates an ICMP \emph{Packet Too Big} response}
\end{figure}

\subsubsection{Sending packets to peers}

The following implementation combines the previously introduced functionality into a complete packet transmission routine:
\begin{figure}[H]
  \begin{minted}{rust}
impl Peer {
    fn send(&self, bytes: Bytes) -> Result<(), SendDatagramError> {
        match self.get_connection() {
            Ok(conn) => {
                // check first if packet fits into MTU
                if let Some(max) = conn.max_datagram_size() {
                    // if not, notify sender to reduce packet size
                    if bytes.len() > max {
                        self.handle_too_big(bytes, max);
                        return Ok(());
                    }
                }

                // simply send bytes to the connection
                conn.send_datagram(bytes)
            }
            Err(e) => {
              eprintln!("unable to connect to {}: {:?}", self.id, e);
              Ok(())
            }
        }
    }

    fn handle_too_big(&self, bytes: Bytes, mtu: usize) {
        // parse bytes into an ip slice
        let ip = IpSlice::from_slice(&bytes[..]).unwrap();
        // create an icmp response based on original packet
        let response = fragmentation_needed_response(&ip, &bytes[..], mtu);
        // send response to the TUN interface
        let _ = self.to_network_tx.send(response.freeze());
    }
}
  \end{minted}
  \caption{Complete packet transmission function for a peer}
\end{figure}

Receiving datagrams is comparatively straightforward and consists primarily of repeatedly calling \\ \texttt{conn.read\_datagram()}
and forwarding the received packets to the TUN device using \\ \texttt{to\_network\_tx.send(bytes)}.

By integrating the previously described components, including configuration management,
routing, peer communication, and packet handling, the resulting implementation provides
a functional peer-to-peer VPN solution in which peers are configured locally.

\subsection{Application Testing Using Minecraft}

To evaluate the application under a practical workload, multiplayer connectivity in
\href{https://en.wikipedia.org/wiki/Minecraft}{Minecraft} was tested between two peers located in different countries.
Initially, the peers were unable to establish a game connection despite successful ICMP communication.

The issue was traced to an incorrect implementation of the ICMP \texttt{Packet Too Big} message.
According to the protocol specification, the message must include a portion of the original IP packet so that the operating system
can identify the affected connection and apply appropriate fragmentation behavior. After modifying the implementation to include
the original packet payload, stable multiplayer communication was successfully established.

\section*{Summary}
\addcontentsline{toc}{section}{Summary}

This work presents the design and implementation of \emph{petope},
a peer-to-peer VPN development project created by \theauthor to explore how two computers can be connected directly
across the Internet without requiring manual port forwarding, static public addresses, or a traditional central VPN relay.
The project was motivated by the practical difficulties of accessing self-hosted services and by the desire to understand,
in a hands-on way, how modern mesh VPN systems such as Tailscale and decentralized networking projects operate.
In addition to the technical goal, the work also aimed to produce a solution that could later be used for private remote access and multiplayer gaming.

The research phase examined several existing approaches to decentralized connectivity and peer discovery.
Particular attention was given to the limitations of conventional VPN setups, the role of NAT traversal, and the problem of
discovering peers when no central coordinator is available. Existing solutions and protocols were studied, including Tailscale, Radmin VPN, Yggdrasil,
BitTorrent-style distributed hash tables, gossip-based discovery, and the \texttt{iroh} networking library.
This research clarified the trade-offs between centralized control, usability, security, and decentralization.
It also showed that a practical VPN implementation must solve not only encryption and addressing, but also peer discovery, dynamic routing, packet delivery, and behavior behind NAT and firewalls.

On the implementation side, the project was developed in Rust and structured around a clear progression from
simple networking experiments to a complete application. The initial experiments covered UDP communication, peer discovery,
UDP hole punching, TCP hole punching attempts, and local multicast DNS discovery. These tests were used to identify what works
reliably in realistic network environments and where transport-layer limitations appear. Based on these findings,
the final application was designed to use the \texttt{iroh} library for secure peer identification, connection setup, and path negotiation.
A peer is identified by a cryptographic public key, and the application automatically derives network information from that identity,
reducing the amount of manual configuration required from the user.

The final solution includes local configuration handling, automatic generation of persistent peer keys,
virtual network interface support through a TUN device, packet routing between peers, MTU handling, and message forwarding between
the application and the operating system network stack. The implementation also includes support for reconnection and for updating peer endpoints when network conditions change.
Because VPN traffic must sometimes exceed the path MTU, the project also implements ICMP \emph{Packet Too Big} responses so that hosts can adjust packet sizes correctly.
This proved important during testing and directly affected the reliability of higher-level applications.

The completed system was evaluated through practical tests on two computers and through a multiplayer Minecraft session.
The tests showed that the application can establish a direct peer-to-peer connection after an initial relay-assisted handshake and then switch to a low-latency direct path.
In one test, the first packet experienced a noticeably higher delay, while later packets were delivered with much lower latency,
confirming that peer discovery and direct connectivity were functioning as intended.
A later Minecraft test exposed an error in the handling of ICMP fragmentation messages; after correcting this issue by including the required part of the original packet, stable game connectivity was achieved.
Overall, the work demonstrates that a functional peer-to-peer VPN can be built using existing Rust networking tools and that
the resulting system is practical for self-hosting and gaming scenarios while remaining small enough to understand and extend.
